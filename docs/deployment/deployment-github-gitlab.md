# GitHub Hub + Private GitLab Skills Deployment

## 1. Target topology

```text
GitHub
  team-skill-hub source
        |
        | GitHub Actions
        v
GitHub Container Registry (GHCR)
  ghcr.io/<org>/team-skill-hub:<tag>
        |
        | docker pull
        v
Company deployment host
  team-skill-hub container
        |
        | SSH Deploy Key (read-only)
        v
Internal GitLab
  ai/rd-skills
  ai/customer-skills
        |
        | Push webhook
        v
POST /webhooks/git
        |
        v
validate -> snapshot -> activate
```

The Hub source code can be public or private on GitHub. Skill contents never need to leave the company GitLab.

## 2. Recommended security model

Use a read-only SSH Deploy Key for Skill repository access. Do not grant write permission to the Hub.

Keep these credentials separate:

- MCP caller API keys: `SKILL_HUB_API_KEYS_JSON`;
- admin HTTP key: `ADMIN_API_KEY`;
- GitLab webhook token: `GITLAB_WEBHOOK_TOKEN`;
- GitLab repository credential: SSH Deploy Key, or HTTPS token when SSH is unavailable.

Never commit private keys, GitLab tokens, API keys, or generated environment files to GitHub. The repository ignores `secrets/` and `.env`.

## 3. Publish the Hub image from GitHub

The repository contains:

```text
.github/workflows/docker-image.yml
```

On pull requests it builds the image. On pushes to `main` and tags matching `v*`, it publishes the image to GitHub Container Registry.

Recommended flow:

1. Create the GitHub repository, for example `your-org/team-skill-hub`.
2. Push this Hub repository to GitHub.
3. Ensure GitHub Actions can publish packages.
4. Push to `main` or create a version tag such as `v0.1.0`.
5. Confirm the package exists under `ghcr.io/your-org/team-skill-hub`.
6. Deploy an immutable version tag in production instead of `latest`.

Example:

```text
SKILL_HUB_IMAGE=ghcr.io/your-org/team-skill-hub:v0.1.0
```

## 4. Prepare the internal GitLab Skill repositories

Recommended layout:

```text
GitLab group: ai
├── rd-skills
└── customer-skills
```

Developers keep normal GitLab branch/MR/review workflows. The Hub only needs read access.

### 4.1 Generate a dedicated read-only Deploy Key

On the deployment host:

```bash
mkdir -p secrets
ssh-keygen -t ed25519 -C "team-skill-hub" -f secrets/gitlab_skillhub_ed25519 -N ""
chmod 600 secrets/gitlab_skillhub_ed25519
```

Add `secrets/gitlab_skillhub_ed25519.pub` to each Skill project as a read-only GitLab Deploy Key.

If company policy requires one key per repository, generate separate keys and use separate secret paths in repository configuration.

### 4.2 Pin the GitLab SSH host key

Do not disable SSH host verification.

```bash
ssh-keyscan -t ed25519 gitlab.company.example > secrets/gitlab_known_hosts
chmod 644 secrets/gitlab_known_hosts
```

Verify the fingerprint through a trusted channel with the GitLab administrator before using it.

Test access:

```bash
ssh -i secrets/gitlab_skillhub_ed25519 \
  -o IdentitiesOnly=yes \
  -o UserKnownHostsFile=secrets/gitlab_known_hosts \
  -o StrictHostKeyChecking=yes \
  -T git@gitlab.company.example
```

## 5. Configure GitLab repositories

Copy the SSH example:

```bash
cp config/repositories.gitlab.example.yaml config/repositories.gitlab.yaml
```

Edit the GitLab hostname/group/project names:

```yaml
repositories:
  - id: rd-skills
    provider: git
    git_url: git@gitlab.company.example:ai/rd-skills.git
    branch: main
    webhook_aliases:
      - ai/rd-skills
      - rd-skills
    git_auth:
      type: ssh
      ssh_key_path: /run/secrets/gitlab_ssh_key
      known_hosts_path: /run/secrets/gitlab_known_hosts
```

`webhook_aliases` are useful when GitLab's project path does not exactly match the Hub repository ID.

Keep the customer repository isolated:

```yaml
visibility: [customer]
access:
  read_roles: [customer]
  sync_roles: [admin]
```

and keep the R&D repository internal/developer-only.

## 6. Prepare runtime variables

Copy the template to a local `.env` file, which is ignored by Git:

```bash
cp examples/deployment/gitlab.env.example .env
```

Replace every placeholder. At minimum configure:

```text
SKILL_HUB_IMAGE=ghcr.io/your-org/team-skill-hub:v0.1.0
NODE_IMAGE=docker.m.daocloud.io/library/node:24-bookworm-slim
AUTH_MODE=api-key
SKILL_HUB_API_KEYS_JSON=
ADMIN_API_KEY=<long-random-admin-key>
GITLAB_WEBHOOK_TOKEN=...
GITLAB_SSH_KEY_FILE=./secrets/gitlab_skillhub_ed25519
GITLAB_KNOWN_HOSTS_FILE=./secrets/gitlab_known_hosts
```

Use long random values generated by the company's approved secret-management mechanism.

`ADMIN_API_KEY` is the bootstrap administrator credential. Normal MCP user keys should be created from `/admin` after startup. `SKILL_HUB_API_KEYS_JSON` is optional and retained only for bootstrap/backward compatibility.

## 7. Start with Docker Compose

The GitLab Compose file supports two modes.

For local/internal testing, build the Hub image from the current source tree. The Compose file defaults `NODE_IMAGE` to `docker.m.daocloud.io/library/node:24-bookworm-slim` for faster Docker Hub access, while the Dockerfile itself still defaults to `node:24-bookworm-slim` when built directly:

```bash
docker compose --env-file .env -f docker-compose.gitlab.yml up -d --build
```

The resulting local image defaults to:

```text
team-skill-hub:local
```

You can override the Dockerfile base image when needed:

```text
NODE_IMAGE=docker.m.daocloud.io/library/node:24-bookworm-slim
```

For production, set `SKILL_HUB_IMAGE` to an immutable published image and pull it before starting:

```bash
docker compose --env-file .env -f docker-compose.gitlab.yml pull
docker compose --env-file .env -f docker-compose.gitlab.yml up -d --no-build
```

`--no-build` makes the production intent explicit: use the configured prebuilt image rather than rebuilding on the deployment host.

Check status:

```bash
docker compose -f docker-compose.gitlab.yml ps
curl http://127.0.0.1:8080/health/live
curl http://127.0.0.1:8080/health/ready
curl http://127.0.0.1:8080/metrics
```

At startup the Hub clones each enabled Skill repository, validates all Skills, creates a validated snapshot, and activates it atomically. The named volume preserves registry state, audit history, Git working copies, and validated revisions across container replacement.

The same named volume also preserves dynamic admin configuration, managed API key hashes, MCP observability logs, feedback and Knowledge Candidates. Do not replace it with ephemeral container storage.

Client lifecycle hook events are stored at `<data_dir>/observability/client-events.jsonl` alongside the other observability JSONL streams. The hook endpoint uses the normal Developer API Key / Bearer Token authentication path.

### 7.1 Configure Knowledge / RAG sources

Each Repository can index Markdown, TXT, text-based PDF and DOCX content. Scanned/image-only PDFs are not OCR'd.

Example:

```yaml
knowledge:
  enabled: true
  include:
    - docs/**
    - "**/*.md"
    - "**/*.txt"
    - "**/*.pdf"
    - "**/*.docx"
  exclude:
    - archive/**
    - generated/**
  max_document_bytes: 2097152
  chunk_size_chars: 1400
  chunk_overlap_chars: 180
```

Repository YAML provides bootstrap defaults. After startup these values can be edited dynamically in `/admin`; saving re-syncs the Repository and rebuilds its Knowledge index. Dynamic values persist under `<data_dir>/config/admin-config.json`.

### 7.2 Configure Knowledge feedback publishing through GitLab MR

Knowledge publishing is disabled by default. Enable it per Repository only after the read-only RAG path is working:

```yaml
knowledge_publishing:
  enabled: true
  provider: gitlab
  base_url: https://gitlab.company.example
  project_path: ai/rd-skills
  token_env: GITLAB_WRITE_TOKEN
  target_branch: master
  branch_prefix: skill-hub-knowledge
```

Provide a separate write credential in the deployment environment:

```text
GITLAB_WRITE_TOKEN=<write-token>
```

Do not reuse the read-only sync credential. Repository sync should remain read-only; `GITLAB_WRITE_TOKEN` is used only to create/update a candidate Knowledge file on a source branch and create a Merge Request. The Hub never auto-merges the MR.

Administrators can edit this configuration under `/admin -> Knowledge`. The UI reports whether the configured token environment variable is present but never exposes its value.

## 8. Configure GitLab webhooks

For each Skill repository:

1. Open **Settings -> Webhooks**.
2. Set the URL to `https://<skill-hub-host>/webhooks/git`.
3. Configure the same secret value used by `GITLAB_WEBHOOK_TOKEN`.
4. Enable **Push events**.
5. Keep SSL verification enabled.

In secret-token mode GitLab sends the value in `X-Gitlab-Token`, which the Hub validates before syncing.

A normal update becomes:

```text
Developer merge/push
   -> GitLab Push Hook
   -> resolve project.path_with_namespace
   -> git fetch/reset
   -> Skill validation
   -> validated snapshot
   -> atomic Registry activation
```

If the new revision is invalid, the previous Last Known Good revision remains active. Polling remains enabled as a fallback when a webhook is missed.

## 9. HTTPS token alternative

If SSH is not permitted:

```bash
cp config/repositories.gitlab-https.example.yaml config/repositories.gitlab.yaml
```

Set:

```text
GITLAB_USERNAME=oauth2
GITLAB_TOKEN=<read-only-token>
```

The token is not stored in `git_url`. The Git provider passes credentials through a generated askpass helper while terminal prompts are disabled.

Prefer the narrowest company-approved read-only token and rotate it according to policy.

## 10. Expose MCP through HTTPS

Production MCP endpoint:

```text
https://<skill-hub-host>/mcp
```

Put an HTTPS reverse proxy/load balancer in front of the container. Do not expose plain HTTP port 8080 across untrusted networks.

MCP callers send either:

```text
Authorization: Bearer <api-key>
```

or:

```text
x-skill-hub-api-key: <api-key>
```

Developer credentials should contain only developer/internal roles. Customer credentials should contain only customer roles.

## 11. Codex integration

Configure Codex to use:

```text
https://<skill-hub-host>/mcp
```

and attach the developer API key as an HTTP authorization header if the client configuration supports MCP headers.

`AUTH_MODE=development` is suitable only for local development. Do not use development mode for a network-accessible production service.

## 12. Upgrade the Hub independently from Skills

When a new Hub image is released:

```bash
# change SKILL_HUB_IMAGE in .env to an immutable version tag
docker compose --env-file .env -f docker-compose.gitlab.yml pull
docker compose --env-file .env -f docker-compose.gitlab.yml up -d
curl http://127.0.0.1:8080/health/ready
```

No Skill repository rebuild is required. Skills remain independently versioned in GitLab.

Existing deployments do not need to migrate configuration manually. Repositories without a `knowledge` block receive backward-compatible defaults. Repositories without `knowledge_publishing` remain publishing-disabled, so upgrades never grant write capability implicitly. After upgrading, verify `/admin`, `/health/ready`, and one `search_knowledge` request.

## 14. Network requirements

```text
Outbound from deployment host/container:
  -> Internal GitLab SSH 22, or HTTPS 443 with token auth
  -> GHCR HTTPS 443 for image pulls

Inbound through reverse proxy:
  <- MCP clients HTTPS 443
  <- GitLab webhook HTTPS 443
```

If the internal GitLab is only reachable on the corporate network, run the Skill Hub on a host/network segment that can reach it. GitHub Actions does not need access to the Skill repositories because Skill contents are not baked into the Hub image.

## 14.1 GitLab sandbox acceptance

Before enabling Knowledge publishing on the production Knowledge repository, run the real MR/webhook/retrieval flow against a dedicated sandbox repository.

Prepare a real MR through the Hub:

```bash
export ADMIN_API_KEY='<sandbox-admin-key>'
npm run sandbox:acceptance -- \
  --phase prepare \
  --hub-url https://sandbox-skill-hub.example.com \
  --repository rd-skills
```

The command outputs a Candidate id, unique marker, branch and Merge Request URL. Review and merge that MR manually in GitLab. The CLI intentionally does not auto-merge.

After the human merge, verify the full loop:

```bash
npm run sandbox:acceptance -- \
  --phase verify \
  --hub-url https://sandbox-skill-hub.example.com \
  --repository rd-skills \
  --candidate-id <candidate-id> \
  --marker <marker>
```

The verify phase requires all of the following:

- GitLab MR reconcile reports `merged`;
- a successful `webhook` repository sync is present after the merge timestamp;
- a manual read-only sync still succeeds;
- Knowledge search returns the unique sandbox marker;
- Candidate publication state remains `published` with merged MR state.

This command is an acceptance harness, not a substitute for the real sandbox. Passing its local mock test only proves the harness behavior; production readiness still requires running it against the real GitLab sandbox.

## 15. Recommended production profile

```text
Hub source          GitHub
Hub image           GHCR with immutable version tag
Skill source        Company internal GitLab
Git auth            read-only SSH Deploy Key
Skill update        GitLab Push Webhook + polling fallback
MCP auth            request-scoped API key initially
Admin auth          independent admin key
Persistent state    Docker named volume
External transport  HTTPS reverse proxy
```

This keeps the Hub software lifecycle separate from company Skill content and credentials.
