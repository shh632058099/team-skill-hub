# Team Skill Hub Expert Platform 设计评审

> 评审日期：2026-10-19
> 评审状态：**Changes Requested / 暂不建议进入实现**
> 被评审设计：`docs/superpowers/specs/2026-10-19-expert-platform-design.md`
> 评审方式：完整阅读设计，并与当前 MCP、Agent 资产、权限、SQLite、部署和测试结构交叉核对。
> 范围说明：这是架构设计评审，不是代码实现审查；未修改原设计，未运行部署或提交。

## 1. 总体结论

长期方向合理：保留现有 Team Skill Hub 的 MCP、Skill / Knowledge、候选审核和 Skill Bundle 发布能力；新增 Expert Worker、Runtime Adapter、异步任务、隔离 Workspace 和可审计的执行治理。

但文档目前**尚未达到可以冻结为“最终架构设计”的程度**。发现 4 项实现前必须解决的 P0 设计问题，以及 4 项高优先级架构缺口。主要风险不是技术选型本身，而是接口契约、安全边界和故障恢复语义还没有完全一致。

评审建议：先修订原设计、逐项关闭本报告的阻塞项，再进行第二轮评审。当前不建议以本设计为依据开始建立完整任务队列或 Worker 执行框架。

## 2. Findings

### F-01 [P0 / Blocker] Task 与 Workflow 的 P0 API 契约冲突

**证据：**
- 第 20.1 节（约第 614–620 行）：`submitExpertTask` 可返回 `taskId / workflowId`。
- 第 25 节 P0（约第 730–743 行）：单专家闭环的 MCP 提交明确描述为返回 `workflowId`。
- 第 22 节（约第 654–675 行）列出 WorkflowRun、WorkflowNodeRun 等数据模型。
- 第 25 节 P1（约第 745–758 行）又将 WorkflowDefinition / WorkflowRun / Plan Revision 放在 P1。

**问题：** P0 的交付对象究竟是 ExpertTask，还是一个只有单节点的 WorkflowRun？两者具有不同的生命周期、权限、幂等范围和持久化语义。若 P0 返回 workflowId，却把 WorkflowRun 延后到 P1，API 和数据库没有明确的事实来源；若 Task 和 Workflow 是同一个实体，又会削弱后续 DAG 与重试模型的边界。

**建议：**
1. 明确 P0 的规范 API 和唯一权威 ID。
2. 推荐 P0 以 `taskId` 为主，TaskRun 表示执行 Attempt；Workflow API 在 P1 增加。
3. 如果必须在 P0 就返回 `workflowId`，则必须明确实现最小 WorkflowRun / 单节点模型，并把对应实体、状态、幂等和验收纳入 P0。
4. 删除“taskId / workflowId 二选一”的模糊契约；对外工具命名、响应 Schema 和数据库关系保持一致。

**关闭标准：** 文档中的 P0 API、实体关系、状态查询和验收示例使用同一套 ID 语义。

### F-02 [P0 / Blocker] 长任务事件流的决策互相矛盾

**证据：**
- 第 1.2 节（约第 29–37 行）：推荐 Worker 主动出站长连接。
- 第 14.1 节（约第 466–474 行）：gRPC streaming / WebSocket 仍待验证选择。
- 第 20.2 节（第 630 行）：写明事件订阅可后续增加。
- 已确认决策 #32（第 917 行）：控制 RPC + 服务端事件流。
- 已确认决策 #33（第 918 行）：持久化事件、序号游标、至少一次投递和消费者幂等。

**问题：** 决策表声称已确定事件流，但正文允许把事件订阅整体延期。P0 无法同时满足这两种要求；此外，Hub–Worker 的控制通道和插件进程内部 gRPC 契约被提及，但未明确是否共享协议、身份和版本协商机制。

**建议：**
1. 将“事件流必须存在”与“具体传输协议待验证”区分开。
2. 明确 P0 必须具备控制 RPC、服务端事件流、事件 ID / 序号、ACK 游标、断线补拉和状态快照恢复。
3. 只保留一种 Hub–Worker 主传输；通过 Task 0 技术验证决定 gRPC streaming 或 WebSocket。
4. 明确插件 RPC 与 Hub–Worker 通道是两个独立信任边界，即使复用 gRPC，也不得复用身份和授权上下文。

**关闭标准：** 第 1.2、14、20、25 节与决策 #32 / #33 采用同一要求，不再出现“事件流以后再加”的表述。

### F-03 [P0 / Blocker] P0 自动执行代码的安全边界尚未形成可执行设计

**证据：**
- 第 6.3 节（第 241–247 行）：明确指出独立进程不等于完整安全沙箱。
- 第 7.2–7.3 节（第 258–271 行）：定义工具策略和自动化边界，但没有给出 P0 必须执行的操作系统隔离基线。
- 第 12.1 节（第 430–438 行）：定义独立 Workspace，允许 Git worktree。
- 第 25 节 P0（第 730–743 行）：要求自动分析、修改、构建、测试和创建 PR。

**问题：** “独立进程 + RPC”只解决部分故障隔离，不能限制进程访问其他用户文件、读取主机凭证、使用 Docker socket、访问内网服务或通过任意子进程绕过 Tool Registry。Git worktree 也不是完整安全边界，因为它会共享 Git 的部分底层存储和仓库元数据。设计尚未说明 P0 对不可信任务提示、仓库内容、Skill / Knowledge 和构建脚本采用何种信任假设。

**建议：**
1. 明确 P0 威胁模型：Worker 主机可信，但任务输入、仓库内容、检索内容和 Agent 输出均视为不可信数据。
2. 指定 P0 支持的平台和最低隔离配置：专用 OS 用户、Workspace 路径约束、文件系统 ACL、环境变量白名单、网络出口策略、进程树控制、资源限制和 Secret 隔离。
3. 明确禁止 Agent 直接访问宿主 Docker socket、Worker 注册凭证、管理员密钥及未绑定的仓库。
4. Tool Binding 必须在受控执行器中落地；命令字符串模式匹配只能作为附加信号，不能作为主要授权机制。
5. 对不能达到最低隔离要求的部署环境，默认禁用写入、构建或凭证操作，而不是仅靠提示词约束。

**关闭标准：** 文档给出可测试的 P0 安全基线、允许 / 禁止能力矩阵和失败关闭行为，并覆盖 Windows / WSL2 / Linux 的实际差异。

### F-04 [P0 / Blocker] 用户身份、Worker 身份与任务凭证委托之间缺少端到端契约

**证据：**
- 第 5.1 节（第 163–173 行）：Worker 注册和管理员激活。
- 第 17.2–17.4 节（第 541–563 行）：定义多层 ACL、Workflow 服务身份和 Secret Provider。
- 第 17.5 节（第 565–569 行）：允许创建分支、提交 commit、push 工作分支和创建 PR。
- 当前代码：`src/security.ts:4-35` 提供开发身份 / API Key 身份，`src/security.ts:38-69` 主要实现静态角色和仓库可见性权限；现有 `Principal` 为 `id / roles / tenantId`（`src/types.ts:371-375`）。

**问题：** 设计定义了“谁提交任务”“哪个 Worker 执行”“哪个 Workflow 身份委托”，但没有形成从 MCP 请求到 Worker 本地进程的可验证凭证链。特别是 P0 尚未交付完整 Workflow 服务身份时，Worker 如何获得刚好足以操作目标仓库的授权？Git PR 凭证如何交给工具而不暴露给 Agent 或任意 Shell？

**建议：**
1. 明确三类身份：请求者身份、Worker 机器身份、单次 TaskRun 的委托执行身份。
2. 定义不可由客户端伪造的授权上下文，包含请求者、taskId / runId、scope、目标仓库、允许操作、有效期、策略版本和撤销状态。
3. Worker 每次领取任务、读取 Artifact / Knowledge 和执行写操作时，验证对应权限；不能因 Worker 已激活而自动继承请求者或管理员的全部权限。
4. Git 操作优先采用专用 Bot / GitHub App / GitLab 项目级凭证或等效最小权限机制；创建 PR 的凭证不得具有合入受保护分支的权限。
5. Secret 只交给被授权的 Tool Adapter 或本地凭证代理，不进入 Prompt、通用环境变量、普通日志或 Agent 可任意读取的文件。

**关闭标准：** 增加身份与凭证流转图，并为跨仓库、撤销、过期凭证、越权读取和 PR 权限提供负向测试。

### F-05 [P1 / High] 持久化队列的部署拓扑与恢复边界没有明确冻结

**证据：**
- 第 14–16 节（第 462–531 行）：要求持久化队列、租约、事件补拉和故障恢复。
- 第 22.1 节（第 678–684 行）：要求事务、Outbox、租约并发控制和外部副作用对账。
- 第 24.1 节（第 705–715 行）：数据库选型仍要求实施前检查。
- 当前代码：`src/storage/database.ts:145-203` 使用 Node.js `DatabaseSync`、SQLite WAL、`busy_timeout=5000` 和 `BEGIN IMMEDIATE`；`docker-compose.yml` 当前部署单个 Hub 服务。

**问题：** 设计要求原子领取和恢复，但没有明确 P0 是否只支持单 Hub 实例、数据库是否与现有观测 / Bundle 数据库共用、任务事件与状态使用哪一个事务边界，以及备份 / 恢复时如何处理正在运行的 Worker 租约。SQLite 可以满足受控的单实例首期，但不能把本地文件自动视为多副本共享队列。

**建议：**
1. 明确 P0 的部署拓扑：单 Hub 实例、单权威事务数据库；不宣称多 Hub 高可用。
2. 明确新任务表是复用现有 SQLite 数据库还是独立数据库文件，并说明迁移、备份、恢复和保留策略。
3. 定义任务创建 + 幂等记录 + 入队，以及状态迁移 + 事件 / Outbox 的事务边界。
4. 定义恢复启动时如何将过期租约、未知进程状态和未完成外部操作转为核验流程。
5. 将多 Hub、共享队列和高可用数据库列为后续 ADR，不在首期隐式支持。

**关闭标准：** 有单实例部署图、事务边界、恢复流程和数据库备份 / 恢复验收案例。

### F-06 [P1 / High] 事件序号、确认游标与 Worker 本地持久化语义仍不完整

**证据：**
- 第 4.1 节（第 150–157 行）：Worker 需持久化未上报事件。
- 第 14.2 节（第 476–482 行）：定义领取、租约和 Worker 启动记录。
- 第 15.1 节（第 484–495 行）：定义唯一 Event ID、单调序号、ACK 游标和 Outbox。
- 第 22 节（第 654–675 行）：数据库模型只列出通用 Event 实体。

**问题：** 设计尚未明确序号由 Hub 还是 Worker 分配、事件流是每个 TaskRun 一个序列还是多个来源合并、Worker 本地事件日志何时确认删除，以及 Hub 重放与 Worker 重发之间如何去重。仅有 Event ID 和序号还不足以确定断线恢复协议。

**建议：**
1. 分开定义 Hub 权威业务事件序列和 Worker 来源事件 ID；明确唯一权威序号的分配者。
2. 定义 ACK 是“已接收”还是“已持久化 / 已应用”，并规定客户端只有在何时可以推进游标。
3. 定义 Worker 本地事件日志的持久化介质、保留、重放和磁盘满时行为。
4. 为重复、乱序、序号缺口、旧 Attempt、旧租约和事件保留期过期定义明确的协议响应。
5. 保证任务事实来自 Hub 持久化状态；Worker 事件用于证据和恢复，不能由任意迟到事件直接覆盖当前状态。

**关闭标准：** 以一个完整的断线—重连—补拉时序图和协议测试明确以上行为。

### F-07 [P1 / High] P0 所需插件信任链不能完全依赖 P2 插件注册中心

**证据：**
- 第 6.3 节（第 241–247 行）：Adapter 是独立进程。
- 第 18 节（第 571–589 行）：完整插件注册、审核发布和撤销机制。
- 第 25 节 P0（第 730–743 行）：P0 已需要实际 Runtime Adapter 执行任务。
- 第 25 节 P2（第 760–768 行）：完整 Plugin Registry 作为后续能力。

**问题：** 完整插件 UI 可以后置，但 P0 已经需要在 Worker 主机上运行 Adapter 代码。若没有最小来源校验、固定版本和允许列表，插件进程可能成为绕过工具权限的入口。文档当前提到后续可增加签名制品，但没有定义首期信任根。

**建议：**
1. P0 不实现通用插件市场，但必须有管理员配置的 Adapter 允许列表。
2. Adapter 固定版本、来源、内容摘要、协议版本和依赖；启动前验证这些信息。
3. 未知版本、摘要变化、协议不兼容或被撤销的 Adapter 必须拒绝启动。
4. 明确 P0 采用预装受信任二进制、受控构建制品或其他具体供应链信任方案；不能以“独立进程”代替来源验证。

**关闭标准：** 有最小插件信任与撤销流程及对应负向测试。

### F-08 [P1 / High] TaskRun 状态机缺少完整转换表与竞争条件规则

**证据：**
- 第 8.3 节（第 310–312 行）：WorkflowRun 状态。
- 第 15.3 节（第 501–505 行）：TaskRun 状态。
- 第 16 节（第 507–531 行）：取消与恢复流程。
- 第 22.1 节（第 678–684 行）：事务和并发控制原则。

**问题：** 状态枚举已有较多内容，但没有列出允许的状态迁移、触发方、事务前置条件及终态规则。例如，取消与完成并发、租约过期与续租并发、确定性失败与重试请求并发时，谁有权决定最终状态仍需推导。状态枚举本身不能代替状态机规范。

**建议：**
1. 在 P0 明确 Task / TaskRun 的允许状态转换表、终态和可重试状态。
2. 为每次迁移定义触发者、前置状态、Attempt / lease fencing 校验、事务写入和事件输出。
3. 明确取消请求与成功完成并发时的仲裁规则；取消结果、进程清理和外部副作用核验分开记录。
4. 旧 Attempt 的结果只能归档，不能更新新 Attempt 或父任务状态。
5. 将非法转换、重复命令和并发竞态纳入自动化测试。

**关闭标准：** 状态迁移表覆盖所有 P0 状态，并能生成直接对应的单元 / 集成测试。

## 3. 33 项决策的整体一致性

大多数决策方向可以保留，不建议为了形式上的“统一”而重选所有技术。建议保留以下主线：

- 插件化 Runtime Adapter + 通用 Worker；
- 每个 TaskRun 独立 Workspace；
- 版本化消息与 Artifact 引用；
- 服务端持久化任务状态、至少一次事件投递和幂等消费；
- 细分 Expert 访问、执行、管理、委托和 Artifact 权限；
- Expert 只能创建受授权的变更与 PR，不能绕过仓库保护策略合入；
- 先做单专家闭环，再扩展 DAG、资源调度和插件生态。

但在将决策表标为“已确认”前，必须解决 F-01 / F-02 的直接冲突；F-03 / F-04 的安全边界必须落成 P0 的强制要求。F-05 至 F-08 可在同一轮设计修订中补齐。

## 4. 建议的修订顺序

1. **先修接口与分期：** 明确 P0 的 Task / Workflow 模型、返回 ID 和事件流要求。
2. **再修安全边界：** 增加 Worker 执行隔离基线、身份委托链和 Git / Secret 凭证模型。
3. **再修可靠性：** 冻结单实例数据库拓扑、事务边界、事件序号 / ACK 和 TaskRun 状态迁移。
4. **最后补插件信任链和验收矩阵：** 区分 P0 最小信任机制与 P2 完整插件市场。
5. 重新评审修订后的原设计，并逐项标记每个 Finding 为已关闭、部分关闭或未关闭。
6. 设计评审通过后，再以通过版本生成实施计划。此前已有的 P0 实施计划只能作为草稿，不代表设计已获批准。

## 5. 最终评审意见

**当前结论：Changes Requested。**

没有发现需要推翻整体方向、从头另选 Agent 框架的理由；但当前文档对 Task / Workflow 的 P0 契约、事件流决策、安全执行边界和凭证委托尚未闭合。若直接进入编码，极易导致任务数据模型返工，或在真实 Worker 上形成超出预期的本机权限边界。

本报告完成的是设计审查与差异分析，不代表已修订原设计，也不代表 P0 已开始实现。
